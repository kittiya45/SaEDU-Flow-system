คู่มือนักพัฒนา — SAEDU Flow

ระบบเสนอเอกสารอิเล็กทรอนิกส์ กนค. คณะครุศาสตร์ จุฬาฯ — เอกสารนี้สรุปสถาปัตยกรรม วิธีพัฒนา วิธี deploy และกับดักที่คนก่อนหน้าเจอมาแล้ว อ่านให้จบก่อนแก้โค้ดครั้งแรกนะคะ

สารบัญ
1. สถาปัตยกรรมภาพรวม 2. เริ่มพัฒนาในเครื่อง 3. โครงไฟล์และลำดับโหลดสคริปต์ 4. ฐานข้อมูลและ RLS 5. การ Deploy 6. กับดักที่พบบ่อย (อ่านก่อนแก้บั๊ก!) 7. เครื่องมือนักพัฒนาในแอป (ROLE-DEV) 8. บริการภายนอกและ Secrets

1สถาปัตยกรรมภาพรวม

Vanilla JS SPA — ไม่มี framework ไม่มี bundler โค้ดทุกไฟล์รันตรง ๆ ในเบราว์เซอร์จาก static file ขั้นตอน build มีอย่างเดียวคือคอมไพล์ Tailwind CSS

  • Frontend: ไฟล์ .js ที่ root ทั้งหมด — แชร์ global scope เดียวกัน (ไม่มี module) โหลดด้วย defer ตามลำดับใน index.html
  • Backend: Supabase (Postgres + Auth + Storage + Edge Functions) — เรียกผ่าน PostgREST ด้วย fetch ตรง ๆ (helper dg/dp/dpa/dd ใน config.js) ไม่ใช้ supabase-js query builder (ใช้เฉพาะ sb.auth.*)
  • Hosting: Vercel — auto-deploy ทุกครั้งที่ push ขึ้น branch main
  • เอกสารเชิงลึกที่สุดคือ CLAUDE.md ที่ root ของ repo — อัปเดตล่าสุดเสมอ อ่านคู่กับไฟล์นี้

2เริ่มพัฒนาในเครื่อง

git clone https://github.com/kittiya45/SaEDU-Flow-system.git
cd SaEDU-Flow-system
npm install
npm run build        # คอมไพล์ tailwind.css → styles.tailwind.css (ไฟล์นี้ gitignore ไว้ ต้อง build เอง)
python3 -m http.server 8000
# เปิด http://localhost:8000

ถ้ากำลังแก้ class Tailwind ในไฟล์ .js ให้รัน npm run watch แทน npm run build เพื่อให้ CSS ตามทันตลอด

ℹ️ไม่มี lint/test ในโปรเจกต์ — ตรวจงานโดยเปิดเว็บแล้วกดใช้ฟีเจอร์จริง ระบบชี้ไปที่ฐานข้อมูล production เสมอ (ไม่มี staging) — ระวังตอนทดสอบฟีเจอร์ที่เขียนข้อมูล

3โครงไฟล์และลำดับโหลดสคริปต์

ไฟล์หน้าที่
config.jsค่าคงที่ทั้งหมด (DTYPES, POSS, CLUBS, RTH, CAN ฯลฯ), helper API (dg/dp/dpa/dd), global state (CU, CV, SETT), error logger
utils.jshelper UI: svg(), esc(), fd(), showConfirm(), showAlert(), addWorkingDays()
events.jsevent delegation กลาง — ปุ่มทุกปุ่มใช้ data-action แล้วมาแตกที่นี่
auth.jslogin/สมัครสมาชิก (Supabase Auth), session refresh, _enterAppAsUser()
homeViews.js / docList.js / docForm.js / docDetail.jsหน้าหลัก 4 หน้า: ภาพรวม, รายการเอกสาร, ฟอร์มสร้าง/แก้, รายละเอียด+อนุมัติ/ตีกลับ
workflow.js / docSign.js / docNum.jsขั้นตอนอนุมัติ, modal ลงนาม, ออกเลขหนังสือ
notif.jsอีเมล (Resend) + LINE OA + ตรวจเอกสารเลยกำหนด/auto-approve
sysAdmin.js / docTypeAdmin.js / admin.jsจัดการระบบ (ตั้งค่า, ข้อมูลอ้างอิง), ประเภทเอกสาร, จัดการผู้ใช้
dev.jsเครื่องมือนักพัฒนา (หน้าที่คุณกำลังใช้อยู่)
layout.js / boot.jssidebar + router nav(), ตัวเริ่มระบบ
supabase/ไม่ใช่โค้ดแอป — SQL สำหรับรันมือใน Supabase SQL Editor + source ของ Edge Functions
⚠️ลำดับโหลดสคริปต์ใน index.html สำคัญมาก — ทุกไฟล์แชร์ global scope เช่น docDetail.js จงใจ override ฟังก์ชัน doAcceptFwd() ของ docList.js (โหลดทีหลังชนะ) ถ้าสลับลำดับพฤติกรรมจะเปลี่ยนเงียบ ๆ

4ฐานข้อมูลและ RLS

ตารางเก็บอะไร
usersบัญชีผู้ใช้ — auth_uid ลิงก์ไป auth.users (อย่าเดาว่า auth_uid === id)
documentsเอกสารหลัก (status, doc_type, created_by, forwarded_to_id)
workflow_stepsขั้นตอนต่อเอกสาร (pending/active/done/rejected)
document_filesไฟล์แนบ (ชี้ Storage bucket "documents")
document_historyappend-only — ห้ามลบ (dd() บล็อก + RLS บังคับ)
notificationsappend-only — log อีเมล/LINE คอลัมน์เวลาใช้ sent_at ไม่ใช่ created_at
app_settingsตั้งค่าระบบ + ข้อมูลอ้างอิง (clubs_json, positions_json ฯลฯ) — แก้ผ่าน UI "จัดการระบบ" ได้เลย ไม่ต้องแก้โค้ด
system_logsJS error จากเบราว์เซอร์ผู้ใช้ — ดูในแท็บ "บันทึกระบบ" ของ Dev Panel

กติกา RLS ที่ต้องรู้

  • RLS เปิดอยู่ทุกตารางใน production — ตารางใหม่ต้องมีทั้ง policy และ ENABLE ROW LEVEL SECURITY ไม่งั้นแอปอ่าน/เขียนไม่ได้ (ไม่มี default-allow)
  • is_admin() (ฝั่ง SQL) = ROLE-SYS, ROLE-STF ใช้ gate ตาราง config และการจัดการ users — ส่วน is_dev() = ROLE-DEV แยกต่างหาก มี policy คู่ขนานชุด *_dev ให้สิทธิ์แคบกว่า (ดู create_dev_role.sql)
  • ผู้ใช้อ่านแถว users ได้เฉพาะของตัวเอง — ถ้าต้องการชื่อ/ตำแหน่งของคนอื่น ให้ query view user_directory เสมอ query ตาราง users ตรง ๆ จะได้ [] เงียบ ๆ ไม่ error
  • ไฟล์ SQL ทั้งหมดอยู่ใน supabase/ พร้อมคอมเมนต์บอกลำดับการรัน — เริ่มอ่านจากหัวข้อ "supabase/ folder" ใน CLAUDE.md

5การ Deploy

เว็บ (Vercel)

git add -A && git commit -m "..." && git push origin main
# Vercel รัน npm run build ให้เอง (vercel.json) แล้ว deploy — เสร็จใน ~1 นาที

Edge Functions (Supabase)

npx supabase login
npx supabase link --project-ref jrubupvzltxqstzcpoov
npx supabase functions deploy send-email          # หรือ admin-delete-user, admin-set-password,
npx supabase functions deploy send-line            # convert-docx, send-line
npx supabase functions deploy line-webhook --no-verify-jwt   # ตัวนี้ต้องมี --no-verify-jwt เสมอ!
⛔อย่า deploy Edge Function ผ่านหน้าเว็บ Dashboard — เคยสร้าง function ใต้ URL slug คนละชื่อกับที่ตั้งแบบเงียบ ๆ ทำให้ endpoint จริง 404 ใช้ CLI เท่านั้น

SQL migration

ไม่มีระบบ auto-migrate — SQL ทุกไฟล์ใน supabase/ รันมือใน Dashboard → SQL Editor ไฟล์ส่วนใหญ่ idempotent (รันซ้ำได้) อ่านคอมเมนต์หัวไฟล์ก่อนรันทุกครั้ง

6กับดักที่พบบ่อย — คนก่อนหน้าเจอมาแล้วทุกข้อ

  • "แก้ CSS/JS แล้วหน้าเว็บไม่เปลี่ยน" → 90% คือลืมบัมป์ ?v=N ใน index.html (ทั้ง script และ styles.tailwind.css) หรือผู้ใช้ยังไม่ hard-refresh
  • เรียก Edge Function แล้ว "Failed to fetch" เงียบ ๆ → ห้ามส่ง header object H ตรง ๆ (มี Prefer ที่ CORS ของ functions ไม่รับ) ให้สร้าง header ใหม่: {apikey:SK, Authorization:H.Authorization, 'Content-Type':'application/json'}
  • showConfirm()/showAlert() ล้าง modal ทั้งกล่อง → ถ้าจะอ่านค่าฟอร์มใน modal หลัง confirm ต้อง capture ใส่ตัวแปรก่อนเรียก (ดูตัวอย่าง doSetDocNumber() ใน docNum.js)
  • ห้ามสร้างชื่อ class Tailwind แบบต่อ string (`bg-${color}`) — ตัว build จะหา class ไม่เจอ สไตล์หายเงียบ ๆ ให้ทำ lookup table ของ class เต็ม ๆ แทน
  • raw fetch ที่ข้าม helper ต้องใช้ H.Authorization — ถ้าใช้ 'Bearer '+SK จะกลายเป็น anon role แล้ว RLS ปฏิเสธเงียบ ๆ (UI ขึ้นสำเร็จแต่ข้อมูลไม่เปลี่ยน) และต้องเช็ค r.ok เองเสมอ
  • dg() อาจคืน error object ไม่ใช่ array — เช็ค Array.isArray() ก่อนใช้ .length ทุกครั้ง (ชื่อคอลัมน์ผิดจะได้ error object ไม่ใช่ [])
  • ลบผู้ใช้ต้อง unlink FK ทุกตัวก่อน — ดูลำดับใน _admDelConfirmed() (admin.js) ถ้าเพิ่มคอลัมน์ใหม่ที่อ้าง users.id ต้องเพิ่ม unlink ด้วย
  • ค่าจากคอลัมน์ free-text ต้อง esc() ก่อนใส่ HTML เสมอ (เช่น department) — กัน XSS
  • อนุมัติ/ตีกลับไม่ atomic (REST หลายคำสั่งต่อกัน) — ถ้าพังกลางทางใช้ "ซ่อมสถานะ" ใน Dev Panel หรือ _reconcileDocState()

7เครื่องมือนักพัฒนาในแอป (ROLE-DEV)

ระบบนักพัฒนาแยกขาดจากแอดมิน ทั้งเมนูและสิทธิ์ฐานข้อมูล — บัญชี role "นักพัฒนา" (ROLE-DEV) เห็นเมนูเดียวคือ "นักพัฒนา" (แอดมินไม่เห็น/เข้าหน้านี้ไม่ได้) ภายในมี 5 แท็บ:

  • สุขภาพระบบ — นับแถวตารางหลัก + ตรวจเอกสารสถานะไม่สอดคล้อง + ปุ่มซ่อม
  • บันทึกระบบ — error log จากเบราว์เซอร์ผู้ใช้ / ประวัติการใช้งาน / log การแจ้งเตือน
  • ซ่อมเอกสาร — แก้สถานะเอกสารและขั้นตอนตรง ๆ (ทุกการแก้ถูกบันทึกลง document_history)
  • จัดการระบบ — เนื้อหาเดียวกับหน้าจัดการระบบของแอดมิน (ฝังมาไว้ในนี้): ข้อมูลอ้างอิง (ชมรม, ตำแหน่ง, ประเภทจดหมาย), ตั้งค่าระบบ + ประกาศหน้า Login, แม่แบบอีเมล, workflow template — แก้ผ่านนี่ก่อนเสมอ ถ้าไม่จำเป็นอย่าแก้ hardcode ใน config.js (ค่าใน app_settings override ค่าในโค้ดอยู่แล้ว)
  • คู่มือ & ลิงก์ — หน้านี้ + ลิงก์ GitHub / Supabase / Vercel

สิทธิ์ฐานข้อมูลของ ROLE-DEV (จาก is_dev() — ไม่ใช่ is_admin())

  • ✅ เขียนตาราง config ทั้งหมด (app_settings, email_templates, workflow_templates, doc_types, doc_number_settings, projects)
  • ✅ UPDATE documents / workflow_steps (เครื่องมือซ่อมเอกสาร) และอ่าน/ลบ system_logs, อ่าน notifications
  • ❌ จัดการผู้ใช้ (เห็นเฉพาะแถวตัวเองใน users), ❌ ลบเอกสาร/ไฟล์/ประวัติ, ❌ Edge Functions ฝั่งแอดมิน (admin-delete-user ฯลฯ)

วิธีมอบสิทธิ์นักพัฒนา

  1. รัน supabase/create_dev_role.sql ใน SQL Editor (ครั้งเดียว — รันซ้ำได้)
  2. ให้คนนั้นสมัครสมาชิกตามปกติ → แอดมินอนุมัติบัญชี
  3. หน้า "จัดการผู้ใช้" → ⋮ → แก้ไขข้อมูล → สิทธิ์ = "นักพัฒนา (ROLE-DEV)"
✅ROLE-DEV ไม่ได้สิทธิ์แอดมิน — จัดการผู้ใช้/ลบข้อมูล/อ่านอีเมลผู้ใช้ไม่ได้ จึงปลอดภัยพอที่จะมอบให้นักโปรแกรมเมอร์ที่มารับช่วงดูแลระบบ
